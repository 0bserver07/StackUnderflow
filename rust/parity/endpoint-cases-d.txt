# BATCH D's endpoint case matrix — the unclaimed remainder.
#
# Same row format as `endpoint-cases.txt`, which is batch C's this round:
#
#   <id> | <METHOD> | <path-and-query> | <json body or ->
#
# A LEADING `!` marks a KNOWN-OPEN case: reported in full under a loud banner,
# never fatal. Unported endpoints belong HERE, in the file — "we know" beats
# "nobody looked".
#
# Run it with batch D's ports (C owns :8096/:8097; :8095 is the maintainer's
# live server and is never bound from anywhere):
#
#   STAX_ENDPOINT_CASES=rust/parity/endpoint-cases-d.txt \
#   STAX_ENDPOINT_RS_PORT=8098 STAX_ENDPOINT_PY_PORT=8099 \
#   STAX_ENDPOINT_DIFFS=rust/.parity-state/endpoint-diffs-d \
#   STAX_ENDPOINT_LOGS=rust/.parity-state/endpoint-logs-d \
#   rust/endpoint-parity.sh
#
# ── THE SIDE-EFFECT RULE, AND THE ONE THIS FILE ADDS ─────────────────────────
#
# `!` softens the VERDICT, never the REQUEST (DIV-059/078). Every row below is
# safe to execute on the shared home. Batch D found a second requirement:
#
#   A `!` row must also be able to TERMINATE.
#
# `Verdict::Error` — what the differ books when a socket read times out — is
# NOT downgraded by `!`, and `Tally::exit_code` ranks it ABOVE a divergence, at
# exit 2. An SSE body never ends, so a row for `GET /api/live/stream` would
# fail the whole run as a harness error and take every other row's verdict with
# it. It is therefore absent, and what WAS verified about it is written down in
# `rust/parity/SSE-PROBE-d.md` (DIV-136) rather than guessed at.
#
# Three more endpoints are deliberately absent for the older rule:
#   POST /api/etl/backfill          rebuilds the marts on the shared home
#   POST /api/patterns/dismiss      writes a governance file OUTSIDE the home
#   POST /api/worktrees/attribute   writes the store
# All three are recorded in their modules' doc tables and in the ledger.
#
# ── ORDER IS SIGNIFICANT ─────────────────────────────────────────────────────
#
# The `G-*` writer block MUTATES `config.json`, which both servers share. The
# differ runs Python then Rust for each case in turn, and `settings._save` is
# idempotent, so each row writes the same bytes twice. The block is ordered to
# self-clean and is LAST in the file, after every row that reads a setting or a
# price — an alias is global and `compute_cost` consults it, so an alias left
# set would silently reprice `WI-whatif-*`.
#
# `POST /api/cfg/currency`'s SUCCESS leg is not a row at any position: it
# persists a `currency` key nothing in the API can remove, and any value but
# USD walks into DIV-052. Its two 400 legs are here.
#
# Fixtures this file names, all measured on `.parity-state/fresh`:
#   37c6275a-ff92-4da8-916d-9097b6da1cc9   the ONE static_analysis_findings row
#   -media-tmos-bumblebe-dev-dev-year26-jul26-StackUnderflow   claude, 2 sessions
#
# ID PREFIXES: `P-`, `Q-` and `Y-` are ALREADY TAKEN in `endpoint-cases.txt`
# (projects, qa, yield_route). An id names the dumped body under
# `.parity-state/endpoint-diffs*/`, so a collision after the architect merges
# these rows would silently overwrite one batch's evidence with another's.
# D's groups are therefore SY- / WI- / QL- / PT-, none of which appear there.
#

#   K-*  routes/cfg.py             (RS-5-050..055)

# ── cfg: the WRITER block. LAST in the file, and it self-cleans. ─────────────
#
# `POST` sets one alias, `DELETE` removes it. `settings._save` is
# `json.dumps(data, indent=2)` — the CLI writer — so each row writes the same
# bytes on both sides and the pair leaves `config.json` holding
# `"model_aliases": {}`, which IS the declared default. Stated exactly because
# "restores the file byte for byte" would be the convenient claim and is false:
# one key remains, holding the default, identically on both servers.
#
# Nothing below this line reads a price or a setting. Never reorder past here,
# and never leave the POST as the last row.
G-alias-set         | POST   | /api/cfg/model-aliases         | {"from": "parity/d-proxy", "to": "claude-opus-4-8"}
G-alias-set-again   | POST   | /api/cfg/model-aliases         | {"from": "parity/d-proxy", "to": "claude-opus-4-8"}
G-alias-read        | GET    | /api/cfg/model-aliases         | -
G-alias-in-cfg      | GET    | /api/cfg                       | -
# DIV-146, measured on this file's first run: `!` because the endpoint is a
# NON-IDEMPOTENT writer, and the differ runs Python then Rust against ONE shared
# home. Python's DELETE removes the alias and answers `{"aliases":{}}`; Rust
# then asks to remove an alias that is already gone and correctly answers its
# 404. Both are right. No ordering fixes it — the second server can never see
# the state the first one consumed — so a writer must be IDEMPOTENT to hold a
# green row here, exactly as a stream must be able to terminate (DIV-136).
# `G-alias-set` above IS idempotent, which is why it is green.
#
# The cleanup still happens: Python's leg does the removal, Rust's is a no-op,
# and the two rows below prove the end state agrees on both servers.
!G-alias-del        | DELETE | /api/cfg/model-aliases?from=parity/d-proxy | -
G-alias-del-again   | DELETE | /api/cfg/model-aliases?from=parity/d-proxy | -
G-alias-clean       | GET    | /api/cfg/model-aliases         | -
