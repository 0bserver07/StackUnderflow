# ── GET /api/etl/status — RS-5-071 ───────────────────────────────────────────
#
# STAYS KNOWN-OPEN, and the reason is NOT the port. Measured 2026-07-31 by
# `ETL-BACKFILL-DIFFER.md` §4: the two bodies differ in exactly one leaf,
# `watcher.enabled` — `false` on Python, `true` on Rust — and in nothing else.
#
# `_watcher_env_disabled()` reads `STACKUNDERFLOW_DISABLE_WATCHER` from the
# process environment on every request. `parity/pyserver.py` sets it with
# `os.environ.setdefault(...)` at import, which puts it in the PYTHON
# interpreter only; `endpoint-parity.sh` exports just `STACKUNDERFLOW_HOME` into
# the Rust subshell, so the Rust server never sees the variable and correctly
# reports the watcher as enabled. Both sides are faithful; the harness is
# asymmetric.
#
# Re-measured with `STACKUNDERFLOW_DISABLE_WATCHER=1` in the Rust environment
# too: the `watcher` block is byte-identical. The fix is one word in
# `endpoint-parity.sh`'s rust subshell —
#     export STACKUNDERFLOW_HOME="$HOME_DIR" STACKUNDERFLOW_DISABLE_WATCHER=1
# — and it belongs to the harness owner, not to this batch (the claim forbids
# editing it). Flip this row to `E-etl-status` in the same commit as that
# export; nothing else about the payload blocks it.
#
# Everything else in the body is deterministic against a shared store:
# `marts[*].last_refresh_ts` is READ from `mart_watermark` (a stored string, not
# a reading), `lag_seconds` is an event COUNT despite the name, `coverage` is an
# anti-join, and `current_job` / `last_job` are `null` unless a backfill ran in
# that process inside the last 30 s — which, with no backfill row in this file,
# never happens.
#
# The endpoint is a pure read on a current store. Python's handler calls
# `schema.apply(conn)`, which on an up-to-date store is a single
# `PRAGMA user_version` and writes nothing; the Rust port does not run
# migrations at all (RS-0-025).
!E-etl-status       | GET | /api/etl/status                    | -

# A second, back-to-back read. The payload must not move between two calls a
# few milliseconds apart — this is the row that would catch a `scanned_at`, a
# "seconds since", or a per-request clock reading sneaking into a STATUS
# surface (the DIV-073 / DIV-085 class). It carries the same `watcher.enabled`
# divergence and no other, so it is `!` for that reason alone.
!E-etl-status-again | GET | /api/etl/status                    | -
