# Batch C / ctxreplay — `routes/context_replay.py` (RS-5-061).
#
# Format and conventions: see the header of `parity/endpoint-cases.txt`. The
# integrator merges these rows into that file and strips the leading
# `P-by-dir-known` row, which already runs earlier there.
#
# ORDER IS SIGNIFICANT. `deps.current_log_path` is server state, and this
# endpoint's fence reads it whenever no `?project=` / `?log_path=` is given, so
# the project must be selected before the first CR-* row runs.
#
# SIDE EFFECTS: none. Every row is a GET that only reads. Two things that look
# like writes are not:
#   * Python's handler calls `schema.apply(conn)` per request — a MIGRATION.
#     On `.parity-state/fresh` (`PRAGMA user_version` = 30, the newest
#     migration is v030) it iterates zero migrations and writes nothing. The
#     Rust port does not call it at all (DIV-106).
#   * Python memoises the built timeline in a process-local dict
#     (`_CONTEXT_CACHE`). No other endpoint reads it and it never touches disk,
#     so it cannot leak into another case the way DIV-059's pricing cache did.
#     Not ported — DIV-105.
#
# Session ids below are real rows in `.parity-state/fresh`:
#   04a86c63-… project 314 (-media-…-StackUnderflow), 3 messages, seq 2369/3036/3576
#   44b8f238-… project 314, 1276 messages, seq 1285 … 5832062
#   3cf184ca-… project  16 (-Users-…-chimera--worktrees-all-issues), 68 messages
# `seq` is NOT per-session-sequential — it is a global-ish counter — which is
# why the cutoffs are the values they are and not 1/2/3.
