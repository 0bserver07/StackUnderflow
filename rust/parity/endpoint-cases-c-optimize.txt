# Batch C / `optimize` — endpoint differ cases for `routes/optimize.py`.
#
# Format is `rust/parity/endpoint-cases.txt`'s, read that file's header first.
# The integrator merges these into the shared file and strips the leading
# `P-by-dir-known` row, which already runs earlier there.
#
# ── ORDER IS SIGNIFICANT, and here it is significant TWICE ───────────────────
#
# The usual reason applies (`deps.current_log_path` is server state). The second
# reason is specific to this module: `/api/optimize` returns `"cache": "hit"` or
# `"cache": "miss"` **in the response body**, so the in-process memo is an
# answer-changer and the rows below are a scripted hit/miss sequence, not a set.
# Both servers start cold and read the same file top to bottom, so they agree —
# but reordering, deleting or re-running a single row changes the expected
# bytes of every later row with the same cache key. See DIV-111.
#
# Cache key = (period, sorted(project), sorted(exclude)) + store.db's mtime_ns.
#
# ── the rolling-window caveat ────────────────────────────────────────────────
#
# `7days` / `30days` bound on `now`, so the two servers compute bounds a few
# milliseconds apart and a message inside that gap is a real (if rare)
# divergence — the same property `CD-prov-week` already carries. It bites at
# most ONCE per cache key here, because every later request on that key is
# served from the memo. The `force` row is deliberately on `period=all`, whose
# bounds are `None` on both sides, so the one row that recomputes on purpose is
# the one row with nothing to drift.
#
# ── LAW 7 ────────────────────────────────────────────────────────────────────
#
# `/api/optimize` writes nothing: the detectors only stat/read under
# `~/.claude`, the pricing engine only reads `models.toml`, and the memo is
# process memory. Verified against the sources, not the docstring (DIV-118).
#
# `/api/optimize/prescriptions` reads the same `~/.claude` CLAUDE.md files the
# bloat detector already scanned and writes nothing;
# `/api/optimize/claudemd-preview` is a pure function of the request body — no
# filesystem read at all. Both are case-row-safe; both have rows below.

P-by-dir-known      | POST | /api/project-by-dir | {"dir_name": "-media-tmos-bumblebe-dev-dev-year26-jul26-StackUnderflow"}

# ── deliberately ABSENT rows, with the reason ───────────────────────────────
#
# * **malformed JSON.** pydantic reports
#   `{"type":"json_invalid","loc":["body",<byte offset>],"ctx":{"error":<parser
#   message>}}`, and both the offset and the message come from pydantic-core's
#   own parser. The port emits a fixed `offset 0 / "Expecting value"` shape,
#   which is only verified for leading garbage. Recorded as DIV-119 rather
#   than asserted here — no row claims a shape that was not measured.
# * **the 413 branch.** It needs a body over 2 MB, which does not belong in a
#   line-oriented case file. Covered by a unit test on the rendered error
#   instead (`the_oversize_guard_is_the_413_and_it_counts_bytes`).
# * **an empty request body.** The differ's `-` means "send no body at all",
#   which also drops the `content-type`; FastAPI's answer then depends on the
#   client's framing rather than on the port. Covered by a unit test
#   (`an_empty_body_and_a_non_object_body_fail_differently`).
