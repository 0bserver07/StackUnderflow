# ── cfg: the WRITER block. LAST in the file, and it self-cleans. ─────────────
#
# `POST` sets one alias, `DELETE` removes it. `settings._save` is
# `json.dumps(data, indent=2)` — the CLI writer — so each row writes the same
# bytes on both sides and the pair leaves `config.json` holding
# `"model_aliases": {}`, which IS the declared default. Stated exactly because
# "restores the file byte for byte" would be the convenient claim and is false:
# one key remains, holding the default, identically on both servers.
#
# Nothing below this line reads a price or a setting. Never reorder past here,
# and never leave the POST as the last row.
G-alias-set         | POST   | /api/cfg/model-aliases         | {"from": "parity/d-proxy", "to": "claude-opus-4-8"}
G-alias-set-again   | POST   | /api/cfg/model-aliases         | {"from": "parity/d-proxy", "to": "claude-opus-4-8"}
G-alias-read        | GET    | /api/cfg/model-aliases         | -
G-alias-in-cfg      | GET    | /api/cfg                       | -
# DIV-146, measured on this file's first run: `!` because the endpoint is a
# NON-IDEMPOTENT writer, and the differ runs Python then Rust against ONE shared
# home. Python's DELETE removes the alias and answers `{"aliases":{}}`; Rust
# then asks to remove an alias that is already gone and correctly answers its
# 404. Both are right. No ordering fixes it — the second server can never see
# the state the first one consumed — so a writer must be IDEMPOTENT to hold a
# green row here, exactly as a stream must be able to terminate (DIV-136).
# `G-alias-set` above IS idempotent, which is why it is green.
#
# The cleanup still happens: Python's leg does the removal, Rust's is a no-op,
# and the two rows below prove the end state agrees on both servers.
!G-alias-del        | DELETE | /api/cfg/model-aliases?from=parity/d-proxy | -
G-alias-del-again   | DELETE | /api/cfg/model-aliases?from=parity/d-proxy | -
G-alias-clean       | GET    | /api/cfg/model-aliases         | -
