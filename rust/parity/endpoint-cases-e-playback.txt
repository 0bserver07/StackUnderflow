# Batch E / member `playback` — case rows for `routes/playback.py`
# (RS-5-091 `/api/playback/{session_id}/fs`, RS-5-092 `/api/playback/{session_id}`,
#  RS-5-093 `/api/playback/project/{project_slug}`).
#
# Format and conventions: see the header of `parity/endpoint-cases.txt`. The
# integrator merges these rows into that file, replacing the five `!PB-*` rows
# that live there today, and strips the leading `P-by-dir-known` selection row.
#
# ── SAFETY (law 4) ───────────────────────────────────────────────────────────
#
# Every row is a GET or an unclaimed method on a GET-only path. All three
# endpoints are pure read-side over `messages.raw_json`, `sessions`, `projects`
# and (when present) `captured_events`; the only write in the Python handlers is
# `schema.apply(conn)`, idempotent DDL the harness store already satisfies, and
# the port does not run it at all (DIV-106). Nothing under
# `$STACKUNDERFLOW_HOME` is written by any row below.
#
# ── TERMINATION (law 4, second half) ─────────────────────────────────────────
#
# The `/fs` endpoint decorates each reconstructed file with a risk overlay, and
# that overlay is O(files × four `LIKE` sweeps of `messages`). Measured on the
# harness store (3.9 GB, `messages` a partitioned VIEW): ~0.6 s per sweep, so
# ~2.5 s per file. The fixtures below are chosen so no row reconstructs more
# than two files — see `PB-fs-replay`'s comment. A row against a
# hundred-file session would be minutes and does not belong in a gate.
#
# ── NO ROW DEPENDS ON SERVER STATE ───────────────────────────────────────────
#
# Unlike most of the matrix, these three endpoints never read
# `deps.current_log_path`: the session id and the project slug both arrive in
# the path. The selection row is carried anyway, per batch C's convention, so
# these rows behave identically whether they are run standalone or spliced into
# the middle of the merged file.
#
# ── THE FIXTURES ─────────────────────────────────────────────────────────────
#
#   04a86c63-4cfd-4929-91a3-3edfe80e3e2f  sessions.id 3488, project 314 (this
#       repo). THREE messages, all role=user, so the event stream and the fs
#       snapshot are both EMPTY at every cutoff — which is what makes it the
#       cheap, always-terminating fixture for the required rows.
#   4f6cb3a7-a786-4fe2-8c40-66c5ec02d933  sessions.id 20, 22 messages, 12 of
#       them assistant rows carrying `tool_use` blocks, TWO of which name a
#       `file_path`. Ingested 2026-03-13 from a project nothing in this
#       campaign writes to, so it is stable. This is the fixture that actually
#       exercises the extractor, the excerpt builder and the fs replay.
#   -media-tmos-bumblebe-dev-dev-year26-jul26-StackUnderflow  projects.id 314,
#       two sessions, 1,279 messages. One provider, so `get_project`'s
#       first-row-wins narrowing is not observable here (see DIV finding 8).
